# Hopper (sm_90a, H100/H200) kernels in TIRx

How SM90 differs from the Blackwell (sm_100a) material in the rest of this manual, what the
tvm-tirx helpers provide, and what was measured while writing the SM90 canonical kernels. Use it
whenever the task's target is `sm_90a`. **No tcgen05, no TMEM, no CLC, no `f32x2` packed math**:
none of the Blackwell patterns built on those transfer.

## 1. What Hopper has, and what it lacks

| | Hopper sm_90a | Blackwell sm_100a |
|---|---|---|
| Tensor-core MMA | `wgmma.mma_async` (one warpgroup, accumulator in **registers**) | `tcgen05.mma` (accumulator in TMEM) |
| Operand sources | A from SMEM (ss) or registers (rs); B from SMEM | SMEM / TMEM |
| Bulk copies | TMA (`cp.async.bulk.tensor`), multicast to a cluster | same |
| Pipelines | mbarrier (`try_wait.parity`, expect-tx) | same, plus tcgen05 commit |
| Persistent scheduling | your own (static or atomic); no CLC | CLC (`clusterlaunchcontrol`) |
| Register split | `setmaxnreg` between warpgroups | same, less critical |
| SMs | 132 (H100/H200 SXM) | 148 (B200) |
| SMEM per CTA | 227 KB | 227 KB |
| Packed f32 FMA | **no** (`fma.rn.f32x2` is sm_100+) | yes |

The accumulator living in registers is the main design constraint. An m64n256 f32 accumulator is
128 registers per thread, which limits the tile and the number of accumulators per warpgroup
(see §4).

## 2. The WGMMA protocol

One chain of k-steps for one m64nN tile:

1. **Fence the operand registers** (accumulator, and the A fragment for rs) with
   `T.cuda.wgmma.noop_barrier` / `wgmma.fence_operands`. This stops nvcc from moving accesses across
   the async MMA, or copying the registers.
2. `wgmma.fence.sync.aligned`.
3. The k-step MMAs **back to back**, `scale_d = 0` only on the first step of a new tile.
4. `wgmma.commit_group.sync.aligned`.
5. Later: `wgmma.wait_group.sync.aligned N`, then fence the operands again before touching them.

`tvm_tirx.backend.cuda.lang.wgmma` implements this: `WGMMA(n, dtype)`, `chain(op, acc, a_steps,
b_steps, accumulate=...)`, `wait(n, (acc, count))`, `SmemTile(...).k_step(op, k, base)`. Use it
rather than raw `T.ptx["wgmma..."]`. Two things it gets right that hand-written code got wrong:

- **K steps across swizzle atoms.** A K-major tile holds one swizzle atom of K per row: 32, 64 or
  128 B for SW32, SW64 or SW128. A step past that atom jumps `rows × atom` bytes, not `k × 32`, at
  any swizzle. `SmemTile.k_step` handles the jump. A plain `advance_descriptor(base, k * 32)` silently
  computes garbage as soon as K leaves the first atom: for SW128 that is K > 64 (bf16) or K > 128
  (fp8), and correspondingly earlier for SW64 and SW32.
- **Descriptor format.** The Hopper descriptor differs from tcgen05's: LBO/SBO semantics, no version
  field. tirx-lite's tcgen05 `SmemDescriptor` cannot be reused.

**Anything else touching the accumulator between fence and wait serializes the chain.** ptxas then
issues each wgmma alone (C7514, §7). This includes reading a *different* accumulator
buffer that is already retired while another chain is in flight. Double-buffering a temporary
accumulator to overlap FP8 promotion with the next chain triggers C7514 on every wgmma (measured
in the B2 design), so do not try it.

**Make the warpgroup index warp-uniform.** WGMMA takes descriptors from uniform registers. If the
smem offset comes from `thread_idx // 128`, nvcc treats it as per-thread: the 64-bit descriptor
arithmetic runs in vector registers, with an `R2UR` before every wgmma. Use `T.cuda.warpgroup_id()`
(uniform by construction), or broadcast with `shfl.sync.idx` from lane 0 as DeepGEMM does. In the
FP8 GEMM this was worth 2–3% (`thread_idx` 0.980 → builtin 0.992 → explicit shfl 0.998 of DeepGEMM).
The builtin is slightly behind because it is bound at kernel entry and stays live across `setmaxnreg`.
Once tvm-tirx's `T.cuda.broadcast_warpgroup_id()` lands (sm90-probe ISSUE-003), use it instead. It emits
the broadcast at the call site, so call it only from warp-converged code, e.g. at the top of the
consumer branch. Until then, write the `shfl.sync.idx` yourself.

## 3. Operands and fragments

- **ss vs rs.** ss reads A and B from SMEM descriptors. rs reads A from 4 registers per thread
  (`wgmma.a_fragment_coord`) and is how attention feeds P back as the A operand of P·V without an
  SMEM round trip.
- **K-major only for fp8 (and tf32).** Only f16/bf16 accept MN-major (transposed) SMEM operands.
  An fp8 V in attention, or an NN/TN fp8 GEMM, needs an SMEM transpose (or a pre-transposed layout).
- **Accumulator layout (m64nN, f32).** Thread `t` of the warpgroup holds rows
  `16·(t // 32) + (t % 32) // 4` and `+8`, and columns `8·c + 2·(t % 4) + {0, 1}` for each 8-column
  group `c`. `wgmma.acc_coord(thread, reg)` gives the map. Epilogues and softmax-on-accumulator use
  it. `stmatrix.m8n8.x4` stores two 8-column groups of bf16/f16 per instruction straight from this
  layout into a swizzled SMEM tile for a TMA store.

## 4. Registers: setmaxnreg and the budget

- **The launch contract.** `setmaxnreg` only works when ptxas knows the entry register count:
  - pin it with `KernelAttributes(min_blocks_per_sm=1)` (or `max_registers_per_thread`);
  - without that, ptxas prints C7508 ("setmaxnreg ignored") and drops the instruction;
  - tvm-tirx rejects unpinned use (`SetMaxNRegContractError`), and also rejects a pin that cannot be
    resident (`threads × min_blocks > 2048`).
- **Entry registers.** At 384 threads × 1 block the entry is **168**, and the pool is 168 × 384.
  Splits that fit:
  - **40 / 232** (producer warpgroup / two consumer warpgroups), DeepGEMM's choice and the default
    for 2-consumer GEMMs;
  - 24 / 240 also fits, but spilled once cluster-multicast addressing was added (B2).

  An over-budget `setmaxnreg.inc` waits forever: a silent hang, not an error.
- **Accumulator budget per consumer thread**, at 232–240 registers:

  | Tile per warpgroup | f32 accumulators | Fits? |
  |---|---|---|
  | m64n256, 1 accumulator | 128 | yes (B1) |
  | m64n128 × 2 waves + 1 temporary (FP8 promotion) | 192 | yes (B2, 256×128 CTA tile) |
  | m64n192, 1 + 1 temporary | 192 | yes (B2, 128×192) |
  | m64n256, 1 + 1 temporary | 256 | **spills** |

## 5. Schedules

- **Warp-specialized, persistent.**
  - One producer warpgroup: a single elected thread issues TMA into an N-stage ring (full =
    TMA-tx mbarrier, empty = consumer arrivals).
  - Two consumer warpgroups of 64 rows each run the chains with `wait_group 1`, overlapping chain k
    with the release of stage k-1.
  - At 128×256×64 (bf16), a stage is 48 KB. Only a 3-stage ring (144 KB) leaves room for a 64 KB
    epilogue staging tile within the 227 KB limit; 4 stages (192 KB) do not.
- **Size persistent grids with `max_active_clusters`** (`tvm_tirx.backend.cuda.runtime.occupancy`),
  never `num_sms // cluster`. On H200 at 384 threads and about 200 KB SMEM:

  | Cluster size | Active clusters |
  |---|---|
  | 1 | 132 |
  | 2 | 66 |
  | 4 | **30**, not 33 |

  GPCs do not divide evenly. Compile once, query, and rebuild with the right count.
- **Clusters and multicast.**
  - B1 uses a 2-CTA cluster along M that shares B: each CTA loads half and multicasts it.
  - A stage is released in both CTAs with `MBarrier.arrive_multicast(stage, ranks=range(2))`.
  - Before exit, drain: the producer waits for every stage's last release, so no remote arrival
    targets a finished CTA.
  - Do not park idle warps at a kernel-end cluster barrier.
- **Cooperative vs ping-pong consumers.**
  - Cooperative: both warpgroups work on one tile, splitting M. B1 and B2 do this.
  - Ping-pong: the warpgroups take alternate tiles and hand over through named barriers
    (`NamedBarriers`), so one's epilogue (or softmax) overlaps the other's MMAs. FA3-style attention
    needs ping-pong plus intra-warpgroup overlap of softmax with the next QKᵀ chain.
  - Reserve named-barrier ids that code uses directly (`NamedBarriers(reserved=(...))`); id 0 is
    `cta_sync`.
- **Epilogue.** `stmatrix` into a 128B-swizzled staging tile, `fence.proxy.async`, then a TMA store
  per 64-column box, with `cp.async.bulk.wait_group.read 0` before reusing the tile. In B1 this
  replaced register→global stores and lifted the gated geomean from 0.905× to 0.97× of cuBLAS.
- **k-loop unroll.** `T.serial(KB, unroll=8)` (`#pragma unroll 8`) lets nvcc interleave the next
  k-block's mbarrier wait, empty arrive and scale loads with the current FFMA work. In the FP8 GEMM
  this was the largest single win (~6–7%).

## 6. FP8 block-scaled GEMM (DeepSeek-V3 recipe)

- Hopper has no block-scaled MMA. Each 128-wide K block is a 4-step fp8 chain (`m64nNk32`) into a
  temporary accumulator, followed by `wait_group 0` and the promotion
  `acc += tmp * sfa[row] * sfb[block]`: 64 FFMA per m64n128 wave.
- The promotion stays **serial**, exactly as in DeepGEMM; overlapping it via double-buffering is
  blocked by C7514 (§2). Without promotion the kernel ran at DeepGEMM speed, so the gap was the code
  *around* the promotion, not the promotion itself. Remove that overhead:
  - uniform warpgroup index (§2);
  - `#pragma unroll 8` on the k-loop (§5);
  - read the A scales from SMEM (TMA-loaded per stage) **before** the chain, and form the scale
    products while it runs;
  - stage this tile's B scales in SMEM once per tile;
  - release the empty barrier per warp (lane 0 of each consumer warp).
- **Tile per shape** (`pick_config`):

  | Shapes | Tile | Cluster |
  |---|---|---|
  | N ≤ 2304 | 128×192 | none |
  | K ≤ 1536 | 128×192 | B multicast along M |
  | otherwise | 256×128 (two m64 waves per warpgroup) | A multicast along N |

  This gives geomean 1.00× DeepGEMM over its m=4096 shapes.
- **Accuracy.** Hopper's fp8 tensor-core accumulation inside a 128-wide block is not full fp32: about
  2⁻¹⁵ of Σ|a·b| was measured. That is why promotion happens every 128. Check outputs element-wise
  against an exact reference, with a bound that includes 2⁻¹² (|A|·|B|ᵀ), not just against one ulp of
  the output.

## 7. Reading ptxas performance remarks (A10)

The benchmark prints remarks with every score (`perf_remark: [C75xx] in main_kernel (sm_90a): ...`).
Treat any of them as a bug in the kernel, not as noise:

| Remark | Meaning | Usual cause |
|---|---|---|
| **C7514** | wgmma serialized: "non wgmma instructions reading accumulator registers of a wgmma between start and end of the pipeline stage" | touching an accumulator, or a second retired buffer, while a chain is in flight; a missing operand fence |
| **C7511** | wgmma serialized: "insufficient register resources for the wgmma pipeline" | too many live registers around the chain: shrink the tile, drop an accumulator, or raise the consumers' `setmaxnreg`. Also caused by a non-wgmma *write* to an accumulator register mid-chain (between the fence and the wait), e.g. zeroing or rescaling it in place |
| **C7517** | "wgmma.wait_group is injected ... by compiler to allow use of registers defined by GMMA" | the accumulator is read before your own `wait_group` retires the chain (missing or too-late `wgmma.wait`) |
| **C7508** | `setmaxnreg` ignored: entry register count unknown | no `min_blocks_per_sm` / `max_registers_per_thread` (tvm-tirx now rejects this before ptxas) |
| spill (`N bytes spill stores`) | registers spilled to local memory | accumulator budget exceeded (§4), or a too-small `setmaxnreg` for the producer |

A clean SASS chain is one `WARPGROUP.ARRIVE`, then N back-to-back `HGMMA`/`QGMMA`, with `gsb0` only on
the last. Check with `cuobjdump -sass` when in doubt.

## 8. Known compiler pitfalls (tvm-tirx, at the time of writing)

Each item names the sm90-probe issue that tracks its fix. When that fix is in the installed tvm-tirx, the
workaround is no longer needed.

- **Cluster ids** (ISSUE-002). `T.cuda.cluster_id` / `cluster_cta_id` are re-read with `asm volatile`
  at every use, so they cannot be hoisted out of loops (about 10% in the FP8 GEMM). Until the fix
  lands, read them once into locals:
  `cl = T.alloc_local([2], "int32"); cl[0] = T.cuda.cluster_id("x"); cid = cl[0]`.
- **block_idx // 2** as a cluster index (ISSUE-001) has hit an int32-literal overflow in `LowerIntrin`
  at some N (e.g. N = 11008). Until the fix lands, use the locals above instead.
- **Warpgroup index** (ISSUE-003). `thread_idx // 128` is not warp-uniform (§2). The fix adds
  `T.cuda.broadcast_warpgroup_id()`; until it lands, broadcast with `shfl.sync.idx`.
- **Bind `broadcast_warpgroup_id()` to a local** (ISSUE-008). Its value is a full-mask `__shfl_sync`
  that is re-emitted at every use. A use inside `T.Or`/`T.And`/`T.Select` (a C `||`, `&&` or `?:`)
  runs it with only some lanes, which hangs the warp. The FA3 port's causal mask hung for every
  `seq_len % 8 != 0` that way. Assign it once at kernel entry,
  `wg = txl.local_scalar("int32"); txl.assign(wg, T.cuda.broadcast_warpgroup_id())`, and use `wg`.
- **`T.max` on floats is three instructions.** It lowers to a NaN-propagating compare/select
  (FSETP.GT + FSETP.NAN + FSEL), not FMNMX. In a softmax over 64 accumulator registers per KV block
  that cost the FA3 port about 15% of its instructions. Use `txl.ptx["max.f32"](dst, a, b)`. Write the
  exponent as `S * c - m * c`, with `m * c` precomputed, so it is one FFMA into `MUFU.EX2`.
- **Python in the traced body.** `x if cond else y`, comparisons of loop variables, and `range` loops
  inside `@T.function` become IR, not Python. Compute config decisions outside the function, and use
  `T.constexpr(...)` for compile-time branches.
